# codingAgent 需求文档

## 1. 文档信息

- 项目名称：codingAgent
- 文档状态：初稿，待评审
- 目标版本：MVP
- 目标平台：Windows、macOS
- 计划截止时间：2026-09-02 24:00（北京时间）

## 2. 项目背景

codingAgent 是一个个人独立设计和实现的编程智能体。用户在终端中输入编程任务后，系统与大语言模型交互，由模型决定是否调用本地工具；系统负责解析调用、在本机执行工具、保存执行结果并继续对话，直至任务完成、失败、被取消或达到安全终止条件。

项目不得封装现成 Agent 产品，也不得使用 Agent 框架或 Agent SDK。对话历史与上下文管理、工具定义与本地执行、模型输出解析、Agent 循环、终止条件和错误处理均由项目自行实现。允许使用模型厂商提供的底层 API 客户端库，但不得依赖服务端托管的代码执行或文件工具。

## 3. 项目目标

### 3.1 核心目标

1. 提供接近现代 coding agent 的终端交互体验。
2. 能够自主读取、搜索、创建和修改项目文件，并执行本地命令。
3. 自行完成模型工具调用循环和错误处理，不依赖 Agent 框架。
4. 支持可视化上下文容量、自动压缩和用户主动压缩。
5. 支持项目级与目录级持久记忆。
6. 支持会话持久化、恢复和可测试的结构化事件记录。
7. 兼容多个 Anthropic Messages 协议端点和模型配置。
8. 核心逻辑与终端界面解耦，为后续图形前端预留稳定接口。

### 3.2 非目标

以下内容不属于 MVP 的强制范围：

- 完整图形前端或 Web 前端；
- 多智能体协作；
- 插件市场或第三方插件系统；
- 向量数据库或语义检索式长期记忆；
- 操作系统级强沙箱；
- 服务端托管的代码执行、文件管理或上下文管理；
- 自动提交、推送或创建 Pull Request；
- 支持所有模型厂商协议。

## 4. 用户与使用场景

### 4.1 目标用户

主要用户为在本地代码仓库中工作的开发者。用户能够使用终端、理解代码改动，并负责确认智能体的最终结果。

### 4.2 典型场景

1. 用户在项目目录启动 codingAgent，并描述一个编程任务。
2. Agent 加载适用的项目记忆，搜索和读取相关代码。
3. Agent 运行测试或诊断命令，定位问题。
4. Agent 精确修改一个或多个文件。
5. Agent 再次执行测试，判断任务是否完成。
6. Agent 向用户汇报改动、验证结果和未解决问题。

核心验收场景为：在一个包含失败测试的小型项目中，Agent 自主搜索、阅读和修改代码，并执行测试直至通过。

## 5. 功能需求

需求优先级分为：P0（MVP 必须）、P1（主体功能稳定后实现）、P2（时间允许时实现）。

### 5.1 CLI 交互

- **FR-CLI-001（P0）** 系统应提供 `coding-agent` 命令，并默认以当前工作目录作为项目工作区。
- **FR-CLI-002（P0）** 系统应默认提供占据终端全屏的 TUI，包含可滚动会话区、常驻输入区和状态区，并支持连续多轮输入。
- **FR-CLI-003（P0）** 模型的文本回复应流式显示。
- **FR-CLI-004（P0）** thinking、工具调用、命令输出、错误和最终回复应使用可区分的 TUI 组件与样式；工具详情应可折叠。
- **FR-CLI-005（P0）** thinking 默认折叠，仅显示状态；用户可通过 `/thinking` 切换显示状态。
- **FR-CLI-005A（P0）** thinking 的显示状态不得改变其在协议历史和持久化记录中的原始内容。
- **FR-CLI-006（P0）** 状态区应显示当前 Provider、模型、工作目录和上下文使用情况。
- **FR-CLI-007（P0）** `Ctrl+C` 在任务运行时应优先取消当前模型请求或本地命令，不应立即破坏会话数据。
- **FR-CLI-008（P1）** 输入区应支持多行编辑和命令历史。
- **FR-CLI-009（P0）** `--prompt` 非交互模式应保持普通 stdout 输出，不启动 alternate screen，便于脚本化和录制。

### 5.2 Provider 与模型配置

- **FR-PROV-001（P0）** 系统应支持配置多个 Anthropic Messages 兼容 Provider。
- **FR-PROV-002（P0）** 每个 Provider 应可独立配置别名、Base URL、API key 环境变量名、鉴权方式和模型列表。
- **FR-PROV-003（P0）** 敏感 Base URL 和 API key 不得写入仓库、会话记录或普通日志。
- **FR-PROV-004（P0）** 模型以 `provider/model` 作为内部唯一标识。
- **FR-PROV-005（P0）** `/model` 应列出本地配置的可用模型，并允许切换 Provider 与模型。
- **FR-PROV-006（P0）** 系统不得依赖 Provider 提供模型列表接口。
- **FR-PROV-007（P0）** Provider 层应把文本、thinking、工具调用、用量和停止原因转换为统一的内部事件。
- **FR-PROV-008（P1）** Provider 层应允许为不同兼容端点配置额外请求体、请求头和能力开关。
- **FR-PROV-009（P1）** 切换模型时，系统应检查上下文容量、thinking 和工具调用能力配置是否完整，并给出明确警告。
- **FR-PROV-010（P0）** Provider 层应完整保留 Anthropic `thinking`、`redacted_thinking`、签名、`tool_use` 和停止原因等协议信息，不得因 UI 折叠而丢弃或改写。
- **FR-PROV-011（P0）** 在携带 thinking 的工具调用轮次中，后续请求必须原样回传该 assistant 消息的 thinking 相关内容块。
- **FR-PROV-012（P0）** 切换模型后，旧模型产生的 thinking 内容仍保留在原始会话记录中，但应从新模型的有效请求上下文中移除。

### 5.3 Agent 执行循环

- **FR-AGENT-001（P0）** 系统应自行维护用户消息、模型消息、thinking block、工具调用和工具结果的有序历史。
- **FR-AGENT-002（P0）** 模型返回工具调用后，系统应校验参数、执行本地工具、记录结果，并把对应结果发送回模型。
- **FR-AGENT-003（P0）** 一个模型响应包含多个工具调用时，系统应完整关联每个调用 ID 与结果。
- **FR-AGENT-003A（P0）** Anthropic `tool_result` 内容块必须紧随对应 assistant `tool_use` 消息，并在后续 user 消息的内容数组中排列在普通文本之前。
- **FR-AGENT-003B（P0）** 工具执行失败应通过 `tool_result.is_error=true` 和可操作的错误内容返回模型；系统不得伪造缺失的 `tool_use.id`。
- **FR-AGENT-004（P0）** 系统应根据 Provider 停止原因、最终文本、用户取消、错误和最大循环次数决定是否终止当前任务。
- **FR-AGENT-005（P0）** 每轮任务应具有可配置的最大 Agent 步数，达到上限时停止并向用户说明原因。
- **FR-AGENT-006（P0）** 未知工具、参数校验失败和可恢复的工具错误应作为结构化工具结果返回模型，而不是直接导致进程崩溃。
- **FR-AGENT-007（P0）** 不可恢复的 Provider、存储或内部错误应终止当前轮次，但保留已写入的会话记录。
- **FR-AGENT-008（P1）** 系统应检测连续重复且无进展的同类工具调用，并在超过阈值后停止或请求用户介入。

### 5.4 本地工具

所有文件工具默认以项目工作区为边界。工具返回值必须结构化，并限制发送给模型的内容大小。

#### 5.4.1 文件读取

- **FR-TOOL-READ-001（P0）** `read_file` 应读取 UTF-8 文本文件。
- **FR-TOOL-READ-002（P0）** `read_file` 应支持指定起止行，并返回带行号的内容。
- **FR-TOOL-READ-003（P0）** 对不存在、非普通文件、二进制文件、超大文件和越界路径应返回明确错误。

#### 5.4.2 文件写入与目录创建

- **FR-TOOL-WRITE-001（P0）** `write_file` 应能创建包含内容的新文件。
- **FR-TOOL-WRITE-002（P0）** `write_file` 应能创建空文件。
- **FR-TOOL-WRITE-003（P0）** `write_file` 应支持按参数递归创建缺失的父目录。
- **FR-TOOL-WRITE-004（P0）** 覆盖现有文件前，工具参数必须明确表达覆盖意图。
- **FR-TOOL-DIR-001（P0）** `mkdir` 应支持递归创建目录，并对已存在目录返回幂等成功。

#### 5.4.3 精确修改

- **FR-TOOL-EDIT-001（P0）** `edit_file` 应支持按起止行替换指定范围。
- **FR-TOOL-EDIT-002（P0）** 修改请求应携带期望的原始内容或内容摘要；文件已变化时必须拒绝修改，避免覆盖并发变更。
- **FR-TOOL-EDIT-003（P0）** 修改结果应返回受影响的行范围和简要差异。
- **FR-TOOL-EDIT-004（P1）** `edit_file` 应支持唯一文本匹配替换，并在零匹配或多匹配时拒绝修改。

#### 5.4.4 代码搜索

- **FR-TOOL-SEARCH-001（P0）** `code_search` 应支持纯文本和正则表达式搜索。
- **FR-TOOL-SEARCH-002（P0）** 搜索应支持文件 glob、大小写选项和最大结果数。
- **FR-TOOL-SEARCH-003（P0）** 结果应包含文件路径、行号和匹配内容。
- **FR-TOOL-SEARCH-004（P0）** 系统应优先使用本机 `ripgrep`，不可用时提供功能受限的跨平台回退实现。

#### 5.4.5 Shell 执行

- **FR-TOOL-SHELL-001（P0）** 对模型暴露统一的 `shell` 工具名称。
- **FR-TOOL-SHELL-002（P0）** Windows 默认使用 PowerShell，macOS 默认使用用户 shell，并允许用户覆盖。
- **FR-TOOL-SHELL-002A（P0）** Windows 与 macOS 应使用独立的命令启动、参数传递、取消和进程树清理实现，不得假定 POSIX 信号在 Windows 可用。
- **FR-TOOL-SHELL-003（P0）** Shell 工具应支持工作目录、超时、退出码、标准输出和标准错误。
- **FR-TOOL-SHELL-004（P0）** 输出超过限制时应截断并明确标记，不能无限占用上下文和本地存储。
- **FR-TOOL-SHELL-005（P0）** 用户取消后应终止当前命令及其可识别的子进程，并记录取消状态。
- **FR-TOOL-SHELL-006（P0）** 首版默认自动执行，但工具接口必须携带风险等级和审批策略字段，为后续用户审批预留扩展点。
- **FR-TOOL-SHELL-007（P1）** 后续应支持 `auto`、`ask`、`deny` 三类权限决策。

### 5.5 上下文容量与压缩

- **FR-CTX-001（P0）** 系统应维护每个模型的上下文上限配置。
- **FR-CTX-002（P0）** CLI 应显示已用 token、上下文上限、使用百分比和自动压缩阈值。
- **FR-CTX-003（P0）** 系统应区分 Provider 返回的精确用量与请求前的本地估算值。
- **FR-CTX-004（P0）** 用户可通过 `/compact` 主动触发本地上下文压缩。
- **FR-CTX-005（P0）** 达到可配置软阈值时，系统应在安全边界自动压缩。
- **FR-CTX-006（P0）** 系统应设置低于模型硬上限的保护阈值，避免请求因上下文溢出直接失败。
- **FR-CTX-007（P0）** 压缩结果应保留系统指令、适用的项目记忆、任务目标、关键决策、已修改文件、验证状态、未完成事项和最近消息尾部；裁剪只能发生在完整协议 Exchange 边界，不能拆开 assistant `tool_use` 与 user `tool_result`。
- **FR-CTX-008（P0）** 压缩应为原子操作；任一压缩策略失败、产物为空、校验失败或存储失败时，不得安装该策略的部分结果；系统可尝试独立的确定性兜底策略，只有完整、校验成功且已持久化的 checkpoint 才能原子安装；所有策略均失败时继续使用原上下文并警告用户。
- **FR-CTX-009（P0）** 系统应记录压缩类型、触发原因、压缩前后 token、摘要和保留尾部范围。
- **FR-CTX-010（P1）** `/context` 应展示上下文组成及最近一次压缩信息。

### 5.6 项目与目录记忆

- **FR-MEM-001（P0）** 系统应识别名为 `CODING_AGENT.md` 的项目记忆文件。
- **FR-MEM-002（P0）** 启动时应从项目根目录到当前工作目录逐级查找并加载记忆文件。
- **FR-MEM-003（P0）** 越接近当前工作目录的记忆优先级越高，同时保留来源路径以便诊断。
- **FR-MEM-004（P0）** 记忆内容应由本地程序读取并注入上下文，不依赖 Provider 的记忆工具。
- **FR-MEM-005（P0）** 记忆文件变化后，新一轮请求应使用更新后的内容。
- **FR-MEM-006（P1）** `/memory` 应列出当前生效的记忆文件及其加载顺序。

### 5.7 会话持久化与恢复

- **FR-SESS-001（P0）** 系统应在用户级数据目录中保存会话，不得默认写入项目仓库。
- **FR-SESS-002（P0）** 会话应采用可检查的追加式 JSONL 事件记录。
- **FR-SESS-003（P0）** 会话应记录用户消息、原始模型内容块、工具调用与结果、用量、压缩、模型切换、中断和错误。
- **FR-SESS-004（P0）** 原始事件历史与当前有效模型上下文应逻辑分离；上下文压缩不得删除原始事件。
- **FR-SESS-005（P0）** `coding-agent --resume` 应恢复最近一次适用于当前项目的会话。
- **FR-SESS-006（P1）** `/resume` 应列出并恢复用户选择的历史会话。
- **FR-SESS-007（P0）** 恢复时应从最新有效压缩点和后续事件重建模型上下文。
- **FR-SESS-008（P0）** 每条持久化记录应携带格式版本；读取器应容忍未知的可忽略字段。
- **FR-SESS-009（P0）** 文件末尾存在不完整 JSON 行时，应跳过该行、发出警告并恢复此前完整记录。
- **FR-SESS-010（P0）** 会话记录不得包含 API key、鉴权头或敏感 Base URL。
- **FR-SESS-011（P1）** 用户应能列出、查看元数据和删除本地会话。

### 5.8 Slash 命令

MVP 至少支持以下命令：

- **FR-CMD-001（P0）** `/help`：显示命令帮助。
- **FR-CMD-002（P0）** `/model`：查看或切换模型。
- **FR-CMD-003（P0）** `/compact`：主动压缩上下文。
- **FR-CMD-004（P0）** `/context`：显示上下文容量信息。
- **FR-CMD-005（P0）** `/thinking`：切换 thinking 显示。
- **FR-CMD-006（P0）** `/clear`：开始新的空白会话，且不删除原会话文件。
- **FR-CMD-007（P0）** `/exit`：安全保存并退出。
- **FR-CMD-008（P1）** `/resume`：选择历史会话。
- **FR-CMD-009（P1）** `/memory`：显示当前记忆来源。

### 5.9 前端扩展接口

- **FR-EXT-001（P0）** Agent 核心不得直接依赖终端渲染代码。
- **FR-EXT-002（P0）** 核心应通过稳定的异步事件流输出文本增量、thinking 增量、工具状态、上下文状态、错误和完成事件。
- **FR-EXT-003（P1）** CLI 应仅作为核心事件流的消费者和用户输入适配器。
- **FR-EXT-004（P2）** 可在不修改 Agent 核心的前提下增加本地 HTTP/SSE 或 WebSocket 接口。
- **FR-EXT-005（P0）** 工具目录与 Agent 循环不得将工具来源写死为内置实现；MVP 只保留可注册的工具来源边界，不实现 MCP 协议。

### 5.10 MCP 外部工具扩展

- **FR-MCP-001（P2）** 系统可作为 MCP Client 连接用户明确配置的外部 MCP Server，并将其工具映射到统一工具目录。
- **FR-MCP-002（P2）** 首个 MCP 传输实现应优先支持本地 `stdio`；Streamable HTTP 应在出现远程或多客户端共享需求后再引入。
- **FR-MCP-003（P2）** MCP 工具必须经过与内置工具相同的参数校验、风险/审批策略、超时、取消、脱敏和会话记录链路。
- **FR-MCP-004（P2）** 外部工具名称必须带服务器命名空间，避免与内置工具或其他服务器冲突。
- **FR-MCP-005（P2）** MVP 不将 codingAgent 暴露为 MCP Server，也不监听 MCP 网络端口。

## 6. 安全与隐私需求

- **NFR-SEC-001** API key 必须通过环境变量或未入库的用户级配置提供。
- **NFR-SEC-002** 用户级配置、会话和日志文件应使用当前用户可访问的数据目录，并尽可能收紧文件权限。
- **NFR-SEC-003** 日志与异常展示必须对密钥、鉴权头和敏感端点执行脱敏。
- **NFR-SEC-004** 仓库应提供覆盖密钥、私有配置、会话和日志的 `.gitignore` 规则。
- **NFR-SEC-005** 测试 fixture、快照、示例配置和文档只能使用虚构端点与假密钥。
- **NFR-SEC-006** 文件工具应拒绝通过绝对路径、`..` 或符号链接逃逸项目工作区。
- **NFR-SEC-007** Shell 执行的风险应在界面中可见；首版自动模式不得阻止后续加入审批策略。
- **NFR-SEC-008** 系统不得默认上传遥测、会话或项目内容到模型请求之外的服务。
- **NFR-SEC-009** 文件工具的工作区边界不等同于 OS 沙箱；首版 Shell 无法提供完整文件系统隔离，文档和界面不得作出超出实际能力的安全承诺。

## 7. 质量属性

### 7.1 跨平台

- 同一代码库必须支持 Windows 和 macOS。
- 路径、编码、换行符、Shell 和进程取消逻辑必须具有平台测试。

### 7.2 可测试性

- Agent 核心、Provider、工具、上下文、记忆、存储和 CLI 适配器必须具有清晰接口。
- Provider 测试不得依赖真实付费 API，应使用录制事件或伪造流。
- 文件与 Shell 工具测试必须在临时工作区运行。
- 压缩、恢复、取消和错误路径必须具有自动化测试。
- 新功能与缺陷修复遵循测试先行的 TDD 流程。
- CI 中的项目总语句覆盖率不得低于 85%，总分支覆盖率不得低于 75%。
- 覆盖率门槛不能替代行为验证；Agent 状态转换、Anthropic 内容块配对、文件越界、编辑冲突、压缩回滚和会话恢复必须有显式测试。

### 7.3 可维护性

- 各模块职责单一，不允许把 Provider 解析、Agent 循环、工具执行和 UI 混入同一模块。
- 内部消息和事件模型应独立于任一 Provider SDK 类型。
- 持久化格式必须版本化，并为兼容读取保留迁移策略。

### 7.4 可观测性

- 错误信息应包含操作类型、可恢复性和建议动作，但不得泄露敏感信息。
- 工具执行应记录开始时间、结束时间、状态和耗时。
- 上下文压缩应记录触发原因及压缩前后用量。

## 8. 验收标准

### 8.1 主流程

在隔离的测试项目中，用户提交修复失败测试的任务后：

1. Agent 能加载项目记忆。
2. Agent 能使用代码搜索和文件读取定位相关代码。
3. Agent 能执行测试并取得失败输出。
4. Agent 能精确修改目标文件。
5. Agent 能再次执行测试并取得成功结果。
6. Agent 能给出包含改动和验证结果的最终回复。
7. 整个过程的消息、thinking、工具调用和工具结果均可从本地会话恢复。

### 8.2 上下文压缩

1. 人工降低测试模型的上下文上限后，系统能在软阈值自动触发压缩。
2. `/compact` 能主动触发同一压缩流程。
3. 压缩后仍保留任务目标、关键文件、验证状态和最近消息。
4. 压缩失败时原上下文保持有效。
5. 退出并恢复会话后，有效上下文与压缩前记录保持一致。

### 8.3 跨平台

1. Windows 上能够运行 PowerShell 命令、取消命令并正确处理路径。
2. macOS 上能够运行用户 shell 命令、取消命令并正确处理路径。
3. 两个平台均能创建空文件、递归目录、搜索代码和精确修改文件。

### 8.4 Provider 兼容

1. 能通过用户配置连接百炼 Anthropic 兼容端点。
2. 能通过独立配置连接公司内部 Anthropic 兼容端点。
3. `/model` 切换后，请求发送到对应 Provider，且不暴露真实端点。
4. 缺少 thinking 或 usage 字段时，CLI 能降级显示而不崩溃。

## 9. 开发与仓库约束

- 使用题目发布后新建的公开 Git 仓库并保留完整提交历史。
- 禁止在已推送历史中压缩或改写开发过程。
- 主体模块使用独立 `feature/*` 分支开发，经自动化测试通过后合并。
- 凭据、内部地址、会话数据和日志不得提交。
- 截止时间后不得向提交仓库推送新提交。

## 10. MVP 完成定义

当且仅当所有 P0 需求均已实现，相应自动化测试通过，第 8 节完整主流程至少在一个实际开发平台的干净测试项目中重复完成，且 Windows 与 macOS 均通过安装、文件工具、路径和 Shell 集成验收时，MVP 才视为完成。P1 和 P2 功能不得阻塞 P0 交付。
